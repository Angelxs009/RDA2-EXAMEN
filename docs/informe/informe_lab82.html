Introducción

Casi toda aplicación que muestra datos tiene una pantalla de lista y otra de detalle: el usuario elige un elemento y espera ver, exactamente, la información de ese elemento. Este patrón se conoce como Master-Detail y obliga a resolver una pregunta técnica: ¿cómo sabe la pantalla de destino qué mostrar? En Navigation Compose la respuesta es la ruta: el origen la construye con valores y el destino los recupera del NavBackStackEntry (Android Developers, s. f.-a).

Este laboratorio continúa los anteriores. Sobre el flujo Login → Dashboard del Laboratorio 8.1 se añade una lista de asistentes que, al pulsar un elemento, navega a un detalle con el identificador y el nombre del asistente. Se resuelve también el desafío extra, que vuelve opcional el nombre y usa el operador Elvis para un valor por defecto. Las pruebas se hicieron en un emulador con Android 16 (API 36).

Objetivos

1. Configurar rutas de navegación dinámicas con parámetros múltiples.

2. Recuperar y procesar argumentos desde el NavBackStackEntry.

3. Mostrar los datos en un componente Card de Material 3 con elevación.

4. Verificar la persistencia de los datos del detalle ante la rotación de pantalla.

Marco teórico

Argumentos en la ruta. Una ruta de Navigation Compose puede declarar marcadores entre llaves, como detail/{asistenteId}. Los argumentos de ruta (path) son obligatorios; los de consulta (?nombre={asistenteNombre}) son opcionales y exigen un valor por defecto o aceptar nulos. Cada argumento se declara con navArgument, indicando su tipo (NavType), si admite nulos y su valor por defecto, y se lee desde backStackEntry.arguments (Android Developers, s. f.-a).

Datos mínimos entre pantallas. La guía oficial recomienda pasar solo la información necesaria para que el destino la obtenga, normalmente un identificador, y no objetos completos (Android Developers, s. f.-a). Este principio se retoma en las recomendaciones, pues el laboratorio pasa además el nombre para practicar los parámetros múltiples.

Modelo inmutable. Una data class de Kotlin con propiedades val genera de forma automática equals, hashCode, toString y copy, lo que la hace adecuada para modelar datos que no cambian (JetBrains, s. f.-a).

Nulabilidad y operador Elvis. En Kotlin, un tipo String? admite nulos y el operador ?: devuelve el valor de la derecha si el de la izquierda es nulo, lo que permite declarar un valor por defecto en una sola expresión (JetBrains, s. f.-b).

Card. El componente Card de Material 3 agrupa contenido relacionado en una superficie con forma y elevación configurables mediante CardDefaults.cardElevation (Android Developers, s. f.-b).

Desarrollo

Adaptaciones respecto a la guía

La guía usa el paquete com.puce.safepass y un proyecto con lista de asistentes previa. El repositorio del grupo es EcoTrip 2026 (com.example.myapplication) y no contenía esa lista, por lo que se creó junto con el modelo. El modelo se ubicó en data/model, junto a los demás modelos del proyecto, en lugar de models. El destino se integró al flujo del Laboratorio 8.1: Login → Dashboard → «Ver asistentes» → Detalle.

Paso 1. Modelo de datos

Asistente es una data class con id, nombre y tipo, todos val. Se agregó una lista de cinco asistentes de ejemplo. Uno se llama «Ana», para reproducir el caso de la guía; otro incluye apóstrofo, y otro contiene «&» y «/», caracteres reservados en una URL, para comprobar que los argumentos viajan intactos.

Paso 2. Pantalla de detalle

DetailScreen recibe asistenteId y asistenteNombre como String? y los muestra en una Card con elevación de 8 dp, con las etiquetas «ID de Asistente» y «Nombre». Además de lo pedido, se añadió una barra superior con botón de retorno, para que la pantalla no quede aislada y se pueda volver a la lista desde la interfaz.

Paso 3. Lista clicable

AssistantListScreen muestra los asistentes en un LazyColumn con ListItem. Cada elemento usa Modifier.clickable y llama a la lambda onAsistenteClick(id, nombre), de modo que la pantalla no conoce el NavController. Se añadió una clave estable por elemento (key = id) para que la lista se recomponga con eficiencia.

Paso 4. Ruta con argumentos en el NavGraph

El archivo NavGraph.kt registra dos destinos nuevos. Los fragmentos clave son los siguientes (el listado completo está en el Anexo):

NavGraph.kt: origen de la navegación (lista)

        // Destino 4 (Lab 8.2): lista de asistentes (Master).
        composable("list") {
            AssistantListScreen(
                onAsistenteClick = { id, nombre ->
                    // Navegación con argumentos dinámicos. Uri.encode protege los caracteres
                    // reservados (espacios, "/", "&", "?") para que no rompan la ruta.
                    navController.navigate("detail/${Uri.encode(id)}?nombre=${Uri.encode(nombre)}")
                },
                onSinNombreClick = { id ->
                    // Desafío extra: el argumento opcional «nombre» se omite.
                    navController.navigate("detail/${Uri.encode(id)}")
                },
                onVolver = { navController.popBackStack() }
            )
        }

NavGraph.kt: destino con argumentos (detalle)

        // Destino 5 (Lab 8.2): detalle (Detail). «asistenteId» es obligatorio y
        // «nombre» es un argumento de consulta opcional.
        composable(
            route = "detail/{asistenteId}?nombre={asistenteNombre}",
            arguments = listOf(
                navArgument("asistenteId") { type = NavType.StringType },
                navArgument("asistenteNombre") {
                    type = NavType.StringType
                    nullable = true
                    defaultValue = null
                }
            )
        ) { backStackEntry ->
            // Recuperamos los argumentos del Bundle de navegación.
            val id = backStackEntry.arguments?.getString("asistenteId")
            val nombre = backStackEntry.arguments?.getString("asistenteNombre")

            DetailScreen(
                asistenteId = id,
                asistenteNombre = nombre,
                onVolver = { navController.popBackStack() }
            )
        }

La guía propone primero la ruta detail/{id}/{nombre} y, en el desafío extra, la versión con nombre opcional detail/{asistenteId}?nombre={asistenteNombre}. La entrega usa esta segunda forma, que incluye la primera: con nombre, el comportamiento es idéntico, y sin nombre la ruta sigue siendo válida. El argumento asistenteId es obligatorio y asistenteNombre es String anulable con valor por defecto null.

Al construir la ruta se aplica Uri.encode a los valores. Sin ese paso, un nombre como «Sofía & Pablo / Equipo QA» introduciría caracteres con significado propio en una URL (espacio, «/», «&»), que pueden alterar cómo se interpreta la ruta. Con la codificación, la prueba recupera el texto completo sin alteraciones (ver Resultados).

Desafío extra. Nombre opcional y operador Elvis

En DetailScreen, el texto del nombre se arma con asistenteNombre ?: "Usuario Invitado". Para poder probarlo desde la interfaz, la lista incluye el botón «Abrir detalle sin nombre», que navega a detail/INVITADO-000 sin el argumento de consulta. Es un artefacto de prueba que se retiraría en una versión final.

Al girar el emulador, la Activity se recrea, pero los argumentos pertenecen al NavBackStackEntry, que el NavController restaura, por lo que la tarjeta conserva «Nombre: Ana» (Figura 2). Análisis

Por qué la ruta es el contrato. La ruta detail/{asistenteId}?nombre={asistenteNombre} describe qué necesita el destino y qué es opcional. Esto hace el flujo predecible y depurable, como plantea el contexto del laboratorio: basta con leer la ruta para saber qué recibe la pantalla, sin rastrear variables compartidas.

Argumentos de ruta frente a estado compartido. Una alternativa sería guardar el asistente seleccionado en un ViewModel y leerlo desde el detalle. Funciona, pero acopla ambas pantallas a un estado oculto y complica los enlaces profundos y las pruebas. El paso por argumentos mantiene cada pantalla autocontenida.

Duplicación del dato. Pasar el nombre además del identificador replica información que el destino podría obtener del repositorio por su ID. Es didáctico para practicar parámetros múltiples, pero si el nombre cambiara mientras el detalle está abierto, la tarjeta mostraría un valor desactualizado.

Alcance de lo verificado. Los datos son una lista fija de ejemplo; no hay repositorio, red ni carga asíncrona. Los resultados demuestran el paso y la recuperación de argumentos, no el manejo de estados de carga o error de un detalle real.

Conclusiones

El laboratorio mostró que el paso de argumentos en Navigation Compose es sencillo de implementar y, a la vez, tiene detalles que se pasan por alto: los argumentos opcionales requieren valor por defecto o nulabilidad, y los valores con caracteres reservados exigen codificación. Con esas dos precauciones, la ruta detail/{asistenteId}?nombre={…} permitió mostrar en una Card los datos del asistente elegido, conservarlos al rotar la pantalla y degradar con elegancia cuando falta el nombre.

En mi opinión, lo más valioso fue el caso del nombre con «&» y «/»: la guía no lo menciona y es justo el tipo de dato real que rompe una ruta en producción. Probarlo desde el principio evitó un defecto que, con nombres de prueba sencillos como «Ana», habría pasado inadvertido. También me pareció acertado que la rotación no exigiera código extra, porque confirma que conviene apoyarse en el estado que el framework ya conserva antes de inventar mecanismos propios.

Por último, el laboratorio sugiere una regla práctica: pasar identificadores en la ruta y obtener los datos desde una única fuente. Pasar el nombre es válido como ejercicio, pero en una aplicación con datos cambiantes es una duplicación que conviene evitar.

Recomendaciones

1. Pasar solo el identificador en la ruta y recuperar el resto desde un repositorio, para evitar datos duplicados y desactualizados.

2. Codificar siempre con Uri.encode los valores de texto libre incluidos en la ruta, y probar con nombres que contengan espacios, «/», «&», «?» y acentos.

3. Migrar a rutas tipadas serializables (como en el flujo de EcoTrip), que convierten los argumentos en propiedades tipadas y eliminan las cadenas de nombre de argumento.

4. Retirar el botón «Abrir detalle sin nombre» antes de publicar, o moverlo a una variante de depuración.

5. Cuando el detalle dependa de datos remotos, modelar los estados de carga y error con una clase sellada en el ViewModel.

6. Mantener pruebas de navegación con argumentos en la integración continua para detectar regresiones al cambiar la ruta.

package com.example.myapplication.ui.navigation

import android.net.Uri
import androidx.compose.runtime.Composable
import androidx.navigation.NavType
import androidx.navigation.compose.NavHost
import androidx.navigation.compose.composable
import androidx.navigation.compose.rememberNavController
import androidx.navigation.navArgument
import com.example.myapplication.navigation.EcoTripNavHost
import com.example.myapplication.ui.screens.AssistantListScreen
import com.example.myapplication.ui.screens.DashboardScreen
import com.example.myapplication.ui.screens.DetailScreen
import com.example.myapplication.ui.screens.LoginScreen
import com.example.myapplication.ui.viewmodel.EcoTripViewModel

@Composable
fun AppNavigation(ecoTripViewModel: EcoTripViewModel) {
    // 1. El NavController es el "conductor" de la aplicación.
    val navController = rememberNavController()

    // 2. El NavHost es el mapa de rutas; startDestination define la primera pantalla.
    NavHost(navController = navController, startDestination = "auth") {

        // Destino 1: Login
        composable("auth") {
            LoginScreen(
                onLoginSuccess = {
                    // POR QUÉ: se navega a 'main' y se elimina 'auth' de la pila, para que el
                    // botón "Atrás" no devuelva al login.
                    navController.navigate("main") {
                        popUpTo("auth") { inclusive = true }
                    }
                }
            )
        }

        // Destino 2: Dashboard
        composable("main") {
            DashboardScreen(
                onLogout = {
                    navController.navigate("auth") {
                        popUpTo("main") { inclusive = true } // Destruye el dashboard
                    }
                },
                onAbrirEcoTrip = { navController.navigate("ecotrip") },
                onAbrirAsistentes = { navController.navigate("list") }
            )
        }

        // Destino 3: flujo EcoTrip (formulario y resumen). "Atrás" regresa al Dashboard.
        composable("ecotrip") {
            EcoTripNavHost(viewModel = ecoTripViewModel)
        }

        // Destino 4 (Lab 8.2): lista de asistentes (Master).
        composable("list") {
            AssistantListScreen(
                onAsistenteClick = { id, nombre ->
                    // Navegación con argumentos dinámicos. Uri.encode protege los caracteres
                    // reservados (espacios, "/", "&", "?") para que no rompan la ruta.
                    navController.navigate("detail/${Uri.encode(id)}?nombre=${Uri.encode(nombre)}")
                },
                onSinNombreClick = { id ->
                    // Desafío extra: el argumento opcional «nombre» se omite.
                    navController.navigate("detail/${Uri.encode(id)}")
                },
                onVolver = { navController.popBackStack() }
            )
        }

        // Destino 5 (Lab 8.2): detalle (Detail). «asistenteId» es obligatorio y
        // «nombre» es un argumento de consulta opcional.
        composable(
            route = "detail/{asistenteId}?nombre={asistenteNombre}",
            arguments = listOf(
                navArgument("asistenteId") { type = NavType.StringType },
                navArgument("asistenteNombre") {
                    type = NavType.StringType
                    nullable = true
                    defaultValue = null
                }
            )
        ) { backStackEntry ->
            // Recuperamos los argumentos del Bundle de navegación.
            val id = backStackEntry.arguments?.getString("asistenteId")
            val nombre = backStackEntry.arguments?.getString("asistenteNombre")

            DetailScreen(
                asistenteId = id,
                asistenteNombre = nombre,
                onVolver = { navController.popBackStack() }
            )
        }
    }
}

                .fillMaxSize()
                .padding(innerPadding)
        ) {

                .padding(16.dp),

        ) {

            ) {

                        style = MaterialTheme.typography.labelLarge

package com.example.myapplication

import androidx.compose.ui.test.junit4.createAndroidComposeRule
import androidx.compose.ui.test.onNodeWithText
import androidx.compose.ui.test.performClick
import androidx.test.ext.junit.runners.AndroidJUnit4
import org.junit.Before
import org.junit.Rule
import org.junit.Test
import org.junit.runner.RunWith

/** Lab 8.2: argumentos dinámicos de navegación (Master-Detail). */
@RunWith(AndroidJUnit4::class)
class ArgumentosNavegacionTest {

    @get:Rule
    val composeRule = createAndroidComposeRule<MainActivity>()

    @Before
    fun abrirListaDeAsistentes() {
        composeRule.onNodeWithText("Ingresar al Dashboard").performClick()
        composeRule.onNodeWithText("Ver asistentes").performClick()
    }

    @Test
    fun clicEnAna_muestraTarjetaConNombreAna() {
        composeRule.onNodeWithText("Ana").performClick()
        composeRule.onNodeWithText("Nombre: Ana").assertExists()
        composeRule.onNodeWithText("ID de Asistente: A-001").assertExists()
    }

    @Test
    fun nombreConCaracteresReservados_seRecuperaIntacto() {
        composeRule.onNodeWithText("Sofía & Pablo / Equipo QA").performClick()
        composeRule.onNodeWithText("Nombre: Sofía & Pablo / Equipo QA").assertExists()
    }

    @Test
    fun rotacion_conservaDatosDelDetalle() {
        composeRule.onNodeWithText("Luis Fernando Mora").performClick()
        composeRule.activityRule.scenario.recreate()
        composeRule.onNodeWithText("Nombre: Luis Fernando Mora").assertExists()
        composeRule.onNodeWithText("ID de Asistente: A-002").assertExists()
    }

    @Test
    fun sinNombre_muestraUsuarioInvitado() {
        composeRule.onNodeWithText("Abrir detalle sin nombre").performClick()
        composeRule.onNodeWithText("Nombre: Usuario Invitado").assertExists()
        composeRule.onNodeWithText("ID de Asistente: INVITADO-000").assertExists()
    }
}
